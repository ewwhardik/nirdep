# nirdep

**nir** (Sanskrit निर्, "without") + **dep**. Say it "near-dep". It deletes your
dependencies.

nirdep is two things that need each other. It is a **runtime**: a small set of
modules that do what the most-installed packages on npm do, written against the
Node standard library and nothing else. And it is a **codemod**: a scope-aware
JavaScript rewriter that finds where your code calls those packages and changes
the call sites for you, so removing a dependency is a diff you can read rather
than a weekend you lose.

Zero Dependency Hackathon, track A. Published by Nastik AI. Developed by Hardik.

## The claim, and how to check it in five seconds

```
git clone <this repo> && cd nirdep
node tools/verify.mjs
```

There is no install step, because there is nothing to install. `verify` does not
trust `package.json` — it reads every `.mjs` file under `bin/`, `src/`, `tools/`
and `tests/`, extracts every import specifier by six different syntaxes
(`import from`, bare `import`, dynamic `import()`, `export from`, `require()`,
`createRequire()`), and fails if a single one of them is not a relative path, an
absolute path, a `#` subpath, or a module the running Node itself calls a builtin.
It asks `module.isBuiltin`, not a hand-written list and not `builtinModules` —
that array omits `node:test` and `node:sqlite`, omits subpaths like
`node:fs/promises`, and would let the real npm package named `test` pass as a
builtin. It writes what it found to `deps-proof.txt`.

That is a stronger statement than an empty manifest. An empty manifest says
nobody declared a dependency. This says nobody imported one.

## Requirements

Node 22.17.0 or newer. Nothing else — no compiler, no package manager, no
network. `make` is convenient but optional; every target is one `node` command
and the commands are listed in the Makefile.

## Status

This is a hackathon entry under active construction, so the honest table is the
useful one. Every command in it runs; `make conformance` is the receipt for the
runtime modules underneath them.

| Command       | State   | What it does                                        |
| ------------- | ------- | --------------------------------------------------- |
| `about`       | works   | attribution, licence, live dependency count          |
| `help`        | works   | the command table                                    |
| `scan`        | works   | what is replaceable, what would leave with it, what is wrong |
| `plan`        | works   | show the diff nirdep would apply, and apply nothing   |
| `apply`       | works   | rewrite the call sites, with a syntax gate           |
| `eject`       | works   | copy a runtime module into your tree, licence header intact |
| `guard`       | works   | fail a build if a banned package or a named version is back |
| `conformance` | works   | pass/fail/skip table for every runtime module        |
| `stdlibmd`    | works   | generate the STDLIB log from the code, not by hand   |
| `explain`     | works   | why a given rewrite is safe, or why it was refused   |

The runtime modules declared in `package.json` are being written in that order.
`nirdep/runtime/colour`, `nirdep/runtime/args`, `nirdep/runtime/semver`,
`nirdep/runtime/glob` and `nirdep/runtime/collect` are done, and the CLI above is
built out of them: the command table, the option list, the exit codes and the "did
you mean" are generated by the replacement for commander, the colour is the
replacement for chalk, the decision to use colour at all is made by the replacement
for supports-color, and `--exclude`/`--include` are matched by the replacement for
minimatch. `bin/nirdep.mjs` contains no help string and no argument parsing — if
any of those modules were wrong, the binary would be visibly wrong too.

`scan` is the one to run first, and the only one that is safe to point at a
repository you do not own: it reads and writes nothing.

```
nirdep scan .
```

It reads `package.json`, whichever lockfile is committed — npm v1/v2/v3, yarn
classic, yarn berry, pnpm 5 or 9 — and every source file, then reports where the
three disagree. The number it exists to produce is the blast radius: for each
replaceable dependency, how much of the installed tree is reachable only through
it, computed from the lockfile's own edges rather than from a table somebody
typed. Findings do not fail the build; the only non-zero exit is a file it was
asked to read and could not. The last block of the report says what the scan did
*not* check, which includes the fact that it makes no network request and so is
not a substitute for `npm audit`.

## The advisory table, and what it is not

`scan` also crosses the tree against `src/scan/advisories.mjs`: 40 rows covering
34 packages — the ones nirdep offers to replace, and the supply-chain incidents
that happened beside them. It is a dated table in a source file. It makes no
network request, so it cannot be turned off by a registry outage and it works on a
train. It is also not `npm audit`, and the report says so on every run, next to
the coverage figure and the date the table was last read against its sources.

Two record kinds, because two different things go wrong:

- A **flaw** is a bug with a CVE, a range and a fix. It is matched with
  `runtime/semver` — the module that replaces the package with the ReDoS is the
  module that decides whether you are still exposed to it. `satisfies` runs with
  `includePrerelease`, because `7.5.1-rc.1` is affected even though a resolver
  would not have installed it.
- An **incident** is a release published to do harm, so it carries exact versions
  and no "fixed in": the malicious artefact sits between two innocent ones, and
  there is no upper bound to be below. `hand` records whether that hand was an
  attacker's or the maintainer's own, because a review of the version you approved
  cannot find what was in the version you got.

Four verdicts, not a boolean: `hit`, `clear`, `unversioned` (the table names the
package but not the releases) and `unknown` (the lockfile records a git URL, a
path or a tag, so no comparison applies). "No" and "the table does not say" are
different sentences, and a tool that prints the first when it means the second is
a tool that tells somebody they are safe.

The one test that matters most asserts that every row's own `fixed` version does
*not* satisfy its own affected range. A range with a typo in it reads perfectly
and clears a version that is still exposed.

Read as news, the table is forty incidents. Read as engineering it is four bugs,
each answered with a version bump where a design change was needed, and each of
which came back. [SECURITY.md](SECURITY.md) walks the four, says what nirdep does
instead of each, and lists what none of it claims.

## Failing a build

`scan` reports. `guard` decides, and its product is the exit code: **0** clean,
**1** something came back or a version in the lockfile is one the table names,
**2** a policy it could not read — because a check that did not run is not a
check that passed.

```
nirdep guard .
```

The policy is a file somebody committed, which is the reviewable place for it —
`.nirdeprc.json`, or a `nirdep.guard` section in `package.json`:

```json
{
  "guard": {
    "signals": ["installed", "imported"],
    "advisories": "hits",
    "max": 12,
    "allow": { "yargs": "DEP-14: the flag parser moves with the next release" }
  }
}
```

`signals` is which of the three ways a dependency shows up counts: `declared`
in the manifest, `installed` in the lockfile, `imported` by a source file. An
allow list takes a reason per package, and the reason is printed under the
exemption on every run, because an undated waiver nobody remembers writing is
how a deny list dies. `advisories` is a ladder — `off`, `incidents`, `hits`,
`all` — where each rung contains the one below it. It defaults to `hits`: a
release published to steal wallet keys is a regression whether or not anybody
chose to install it, so silence has to be something somebody wrote down. It is
also the one thing an allow list cannot cover. Naming a package permits it being
*installed*; it is not consent to a particular release of it being malicious, and
the report says so in those words.

Every flag on the command line — `--advisories`, `--max`, `--allow`, `--dev` —
overrules the file only when it was actually typed, and the footer names which
ones spoke.

### As a step in your build

```yaml
name: dependencies
on: [push, pull_request]

jobs:
  nirdep:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: nastik-ai/nirdep@v1
        with:
          advisories: hits
          max: 0
```

There is no install step, and that is the point: the action runs the JavaScript
in this repository with the Node the runner already has. An action that
`npm install`s a dependency checker has added dependencies to the build it is
auditing. (The slug is wherever this repository lands; the action itself is the
`action.yml` in its root, so `uses: ./` works inside the repo — that is how the
workflow in `.github/workflows/guard.yml` tests it against nirdep itself.)

Inputs are `path`, `policy`, `advisories`, `max`, `allow`, `dev`, `annotate`,
`summary` and `fail`; outputs are `exit-code` and `report`. Findings are attached
to the diff as annotations, one per finding, at the line that imports the package
or at the lockfile the version came from — never at a path inside
`node_modules`, which is not a file in the repository. GitHub shows ten
annotations per level and drops the rest without a word, so nirdep shows nine and
says how many it left in the log. `fail: false` reports and leaves the job green,
which is the honest first run on a project nobody has cleaned up yet.

## What the runtime replaces

Five targets, taken to conformance rather than to a demo. The choice is
deliberate: breadth without evidence buys nothing, so each module is judged
against the reference package's own published behaviour. Eleven packages, and
`nirdep conformance` prints the case count for each.

| Module            | State   | Replaces                                                    | Why the standard library is not enough on its own                                                     |
| ----------------- | ------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `runtime/colour`  | done    | chalk, ansi-styles, supports-color, color-convert, picocolors | `util.styleText` has no chainable API, no 256-colour or truecolour, and no level detection             |
| `runtime/args`    | done    | minimist, commander, yargs, yargs-parser                     | `util.parseArgs` is strings and booleans by design: no subcommands, coercion, counts, or generated help |
| `runtime/semver`  | done    | semver                                                       | Node has no version comparison at all beyond `process.versions` string equality                        |
| `runtime/glob`    | done    | minimatch, the matching half of glob                         | `fs.globSync` walks a disk and exposes no reusable string matcher, no brace options, no partial match  |
| `runtime/collect` | done    | lodash, the seventeen calls people actually make             | `structuredClone` throws on a function, and nothing in Node reads or writes `a.b[0].c`, merges, or debounces |

### runtime/colour

About 320 million downloads a week of the packages in that first row. One file,
no configuration, one import (`node:util`, for `stripVTControlCharacters` — the
only part of this Node already got right).

```js
import colour from 'nirdep/runtime/colour';

colour.red.bold('broken');            // chainable, in any order
colour.hex('#ff8800')('warning');     // downsamples to 256 or to 16
colour.bgBlue('two\nlines');          // closed and reopened per line
colour.level = 0;                     // and every chain above goes plain
```

What it gets right that a naive implementation does not: bold and dim share the
close code 22, so closing one must not clear the other; a bright foreground
closes with 39 and not 99; nested styles of the same kind are repaired by
rewriting the inner close into the outer open, innermost first; a background is
closed before every newline and reopened after it, or it paints to the right edge
of a wrapped terminal; greys use the 24-step ramp at 232-255 rather than the
cube diagonal, which would band a gradient into six steps; and `createColour()`
hands back an independent instance, so a library that silences itself cannot
silence the application that imported it.

75 conformance vectors live as data in `tests/vectors/colour/*.json`, hand-written
from ECMA-48 rather than captured from our own output, plus a 33-row detection
matrix in `tests/runtime/level.test.mjs`.

### runtime/args

About 190 million downloads a week. One file, zero imports, two layers, because
the packages split the same way: `parse` is the parser that minimist and
yargs-parser are, and `createCli` is the framework that commander and yargs add on
top of it.

```js
import { createCli, parse, EXIT } from 'nirdep/runtime/args';

const app = createCli({
  name: 'tool',
  options: { colour: { type: 'boolean', default: true } },
  commands: {
    build: {
      positionals: [{ name: 'target', required: true }],
      options: { jobs: { type: 'number', short: 'j', default: 1 } },
      run: (context) => { context.out(`${context.positionals.target}\n`); },
    },
    ship: { describe: 'not written yet', ready: false },   // exits 3, honestly
  },
});
process.exitCode = app.run(process.argv.slice(2));
```

Four decisions in it disagree with minimist on purpose:

- **No automatic number coercion.** minimist turns `--id 0123` into `123` and
  `--version 1.10` into `1.1`. Zero-padded identifiers, version strings and
  hashes all travel through argument parsers. Declare `type: 'number'` and you get
  a plain decimal literal or an `INVALID_VALUE`; `0x10`, `1_000` and `Infinity`
  are refused rather than guessed at.
- **Prototype pollution is closed by absence.** Both minimist advisories
  (CVE-2020-7598, CVE-2021-44906) come from one feature: dot notation, where
  `--__proto__.polluted=yes` becomes an assignment onto `Object.prototype`.
  Nesting a command line is a config file's job, so the feature does not exist and
  the attack has nowhere to arrive. `__proto__`, `prototype` and `constructor` are
  refused as spec keys and again at the assignment site, and five attack strings
  in the suite assert against `Object.prototype` itself.
- **A repeat is last-wins unless the option asked for a list.** In minimist the
  *type* of a field depends on how many times the user pressed the up arrow, so
  every consumer needs `Array.isArray`. Here `multiple: true` makes a field a list
  from its first occurrence, and without it the last value wins.
- **A value-taking option will not swallow the next flag.** `--output --verbose`
  sets output to the string `"--verbose"` in both minimist and `util.parseArgs`.
  Here it is a `MISSING_VALUE` error. A negative number is still a value, and a
  bare `-` is still a positional.

Everything else is the surface those packages are installed for: short clustering
with getopt's rules (`-fo out.txt`, `-foout.txt`, `-o=value`), counts (`-vvv`),
`--no-` negation that a literally-named `--no-cache` option beats, `--`
termination, choices, conflicts, implications, required options, declared and
variadic positionals, environment fallback that an explicit flag overrides,
subcommands with per-command help, help tables measured in visible columns rather
than bytes, and "did you mean" on both options and commands — by optimal string
alignment, so the transposition `sacn` scores one edit against `scan` and beats
`plan`, which plain Levenshtein ties.

Exit codes are fixed and documented: 0 success, 1 our fault, 2 the user's, 3 not
implemented yet. Errors carry a stable `code` and an unstable message; a bad
*spec* throws `SpecError` instead, because that is our mistake and must never be
reported as though the user mistyped something. Help styling arrives as a plain
object of functions that all default to the identity, so this module has no
opinion about colour and does not import the one that does — the two can be
ejected independently, and a test asserts neither imports the other.

94 parser cases live as data in `tests/vectors/args/parse.json`, 27 of them naming
the error code they must throw.

### runtime/semver

About 300 million downloads a week, and the one row here where Node offers
nothing at all: `process.versions` hands you strings, and comparing them lexically
is wrong at the first two-digit minor. One file, zero imports, 43 exports — 38
functions, the error class and four constants — matching the package name for
name, because a codemod that rewrites the import must not force anyone to rewrite
the call sites underneath it.

```js
import { satisfies, subset, minVersion, inc, diff } from 'nirdep/runtime/semver';

satisfies('1.2.3', '^1.0.0');                    // true
satisfies('1.2.3-beta', '>=1.0.0');              // false, as npm resolves it
subset('~1.2.3', '^1.0.0');                      // true
minVersion('>=1.2.3 <2.0.0').version;            // '1.2.3'
inc('1.2.3', 'premajor', 'beta');                // '2.0.0-beta.0'
diff('1.2.3', '1.2.4-alpha');                    // 'prepatch'
```

**Not one regular expression, anywhere.** Every scanner is a loop over character
codes. The reason is CVE-2022-25883: node-semver's range parser backtracked, so
any call site that passed a user-supplied range string could be hung by it. A
scanner that reads each character once cannot backtrack, so the class of bug is
absent rather than patched — and the claim is asserted by a test that strips the
comments and fails if a single `/` survives.

**Checked against the package it replaces, 507,316 times.** A differential
harness called `semver@7.8.5` as a black box across 55 versions, 118 ranges, four
option sets, ten release types and 28 coercion inputs, on every export. 507,244
answers agree. The 72 that disagree were each re-checked against that package's
*own* `satisfies`, and every one is a case where it contradicts itself: 56
`intersects` cells where no version is in both ranges, 16 `subset` cells where
nothing in the sub-range falls outside the containing range. Two more are crashes
rather than answers — `cmp(v, '===', null)` and `satisfies(1.2, '*')` throw a
`TypeError` from inside the reference implementation, while a predicate here
answers `false`.

The sharpest one: **`intersects` is not symmetric there.**
`intersects('1.2.3-beta', '*')` is `false` and `intersects('*', '1.2.3-beta')` is
`true` — same pair, two answers. Here it is `false` both ways, which is what its
own `satisfies` says, and a test checks symmetry across the whole 118×118 grid.

Where the reference is merely strange, this module is strange in the same way,
because parity beats taste when a rewritten call site is on the line:
`inc('1.2.3', 'nonsense')` returns `null` rather than throwing, and `SemverError
extends TypeError` so an existing `catch` still fires. Every throw carries a
stable `code`. A parsed version is frozen plain data with a non-enumerable
`toString`, so `${version}` prints `1.2.3` while `Object.keys` sees only data.

Six tables, 1266 lines, in `tests/vectors/semver/` — inputs chosen by hand,
expectations captured from the reference package and disclosed as borrowed in
[STDLIB.md](STDLIB.md), with the six self-contradicting cells overridden and
argued by name rather than quietly recorded as agreement.

### runtime/glob

More than 100 million downloads a week between the two, and almost nobody
installs either on purpose: minimatch arrives as glob's dependency, and glob
arrives underneath the tooling. Node 22 ships `fs.globSync`, which walks a tree —
but the matcher is what most of that traffic actually is, deciding whether a path
you already have matches a pattern a user already typed. So this file is the
matcher, and its `globSync` is the walk written on top of it. 1149 lines, 17
exports, `minimatch@10.2.6`'s names.

```js
import { minimatch, matcher, braceExpand, globSync } from 'nirdep/runtime/glob';

minimatch('src/deep/a.mjs', 'src/**/*.mjs');       // true
minimatch('src', 'src/**', { partial: true });     // true: could match below
braceExpand('{a,b}{1..3}');                        // six patterns, expanded first
const test = matcher('**/*.test.mjs');             // compile once, filter a list
globSync('src/**/*.mjs', { cwd: '.' });            // sorted, and it is our matcher
```

**Not one regular expression, anywhere — the second time.** minimatch compiles a
pattern to a `RegExp`, and CVE-2022-3517 was that `RegExp` backtracking on a
crafted brace body: the same class of bug as node-semver's CVE-2022-25883, in the
package node-semver depends on. Two modules, one answer, which is the difference
between a policy and a lucky fix. What replaces the compiled pattern is two
nested state-set simulations — one over the segments of a path, one over the
characters of a segment — where every step advances a set of reachable positions
exactly once per token. Work is bounded by positions times tokens, so
backtracking is absent rather than patched. The file contains no forward slash
outside its comments, which is a strange thing to say about a glob matcher and is
the whole point; a test strips the comments and counts.

Because the bound has to be enforced somewhere, three ceilings refuse instead of
hanging: 65536 pattern characters (`TOO_LONG`), 8192 brace expansions
(`TOO_MANY_EXPANSIONS`), 16 levels of brace or extglob nesting (`TOO_DEEP`). A
pattern that merely looks wrong is not an error — an unterminated `[` is literal
text, as it is in a shell — so the only thing refused is cost. `makeRe()` exists
and throws `NO_REGEXP` naming `matcher(pattern)`, because a call site that wanted
a `RegExp` should fail at the call rather than hours later.

**Checked against the package it replaces, 228,852 times.** 222,495 matching
checks over 105 paths and 6,357 surface checks — `braceExpand`, `hasMagic`,
`escape`, `unescape` — against `minimatch@10.2.6` as a black box. 697 cells
disagree, every one with a recorded cause, and the causes are pinned by count so
a new disagreement lands in `unknown` and fails the suite: **576** where their
`[[:print:]]` compiles to the same thing as `[[:cntrl:]]`, its POSIX inverse;
**91** where a non-ASCII character meets a POSIX class, which is our stated limit
(the classes are ASCII tables plus case mapping, so `中` is not `[[:alpha:]]`);
**18** where their `partial` descends into directories that cannot match; **12**
where their brace expander reserves backslash as an internal sentinel, so
`{A..z}` loses ASCII 92 and matches the empty path, while ours keeps all 58
characters of the span.

**And nirdep runs on it.** `src/fs/walk.mjs` compiles this module's `matcher()`
for the `--exclude` and `--include` flags that `scan`, `plan`, `apply` and
`stdlibmd` share. Pruning follows `globSync`'s rule — a directory that matches an
exclude is never opened, and one is only entered when some include could still
match inside it, which is `partial: true` earning its keep in the shipped tool.
Pointed at this repository: 84 files read, `--exclude 'tests/**'` 38,
`--include 'src/runtime/**'` 4.

Five tables, 2035 cases, in `tests/vectors/glob/` — inputs by hand, expectations
captured from the reference package and disclosed as borrowed in
[STDLIB.md](STDLIB.md).

### runtime/collect

Nobody imports lodash for all of it. The calls that survive code review are the
path readers, the deep copy, the deep compare, the merge, the grouping and the two
timers, so that is what this file is: 994 lines, seventeen functions,
`CollectError`, and a frozen default carrying all eighteen names — the shape a
default binding expects, so `_.get(…)` keeps working after the rewrite.

```js
import _ from 'nirdep/runtime/collect';
import { get, merge, cloneDeep, isEqual, groupBy, debounce } from 'nirdep/runtime/collect';

get(config, 'server.hosts[0].port', 8080);   // a path, a default, no throw
merge({ a: { b: 1 } }, { a: { c: 2 } });     // deep, and undefined never overwrites
isEqual(0, -0);                              // true; util.isDeepStrictEqual says false
const save = debounce(write, 200, { maxWait: 1000 });  // trailing by default
```

**Four CVEs, one bug, and the half a blocklist cannot see.** `CVE-2018-3721` was
`_.merge`. `CVE-2020-8203` was `_.set` and `_.zipObjectDeep`. `CVE-2019-10744` was
`_.defaultsDeep`. Same bug three times: a deep write that accepts `__proto__`
writes to every object in the program at once. Those three names are refused here
outright — `ERR_UNSAFE_KEY`, not a silent no-op — and that is the easy half. The
hard half is that `_.set({}, 'toString.polluted', 'yes')` names nothing forbidden.
It walks into the *inherited* `Object.prototype.toString`, materialises it, and
writes there; afterwards an unrelated `_.pick({}, 'toString')` hands the value
back. So a deep write in this module never follows a property the object does not
own. The fix is four lines, and it is why four of the eleven differences below
exist.

**Sloppy mode was doing work you would notice losing.** lodash's dist is not a
module, so a write to a frozen slot or a delete of a non-configurable key quietly
did nothing there — and the same code in an ESM file throws. Ported straight, that
turns silent no-ops into crashes in other people's builds. Every write goes
through `Reflect.set` and every delete through `Reflect.deleteProperty`, which
decline the impossible quietly and still throw on the genuinely dangerous. A
complaint the object raises itself, like `arr.length = {}`, is passed on: it is
the object's answer, not ours. Swallowing that one turned three divergences into
eighty-seven, which is the sort of thing a differential harness tells you within
about three seconds.

**Checked against the package it replaces, 120,000 times.** 8000 seeded rounds
against `lodash 4.18.1` as a black box, every difference pinned by cause and by
count so a new one lands in `unknown` and `unknown` is asserted empty. Eleven
stand, and ten of them are repairs: own-only walking in `set`, `unset`, `pick` and
`merge`; `cloneDeep(new Error(…))` clones the error where lodash returns `{}`;
`omit` copies own keys only, where lodash copies inherited ones — so
`_.omit(Buffer.from('hi'), '0')` comes back with 95 keys including
`Buffer.prototype.inspect` and **throws when you log it**; `merge` into a
primitive returns the primitive rather than a boxed wrapper, keeps a typed array
typed, and merges symbol keys; brackets quote their content, so `a[x.y]` is two
keys where lodash's path regex accepts only numbers and quoted strings and
otherwise reads as if the brackets were absent; and `sortBy` ties two `NaN`s,
where lodash's comparator answers "greater" in both directions, leaving the order
to the sort algorithm and skipping every criterion after it. The eleventh is a
limit, stated rather than hidden: an object iteratee matches partially, but not
with lodash's full partial-array semantics.

**And nirdep runs on it.** `groupBy`, `keyBy` and `sortBy` take any iterable, not
just arrays and plain objects, because the tool needed to group a `Set` — and a
module that cannot do what its own author needed is not a module to hand anyone
else.

Three tables, 147 cases, in `tests/vectors/collect/` — inputs by hand,
expectations captured from the reference package, divergences carrying both
answers and a reason, all disclosed as borrowed in [STDLIB.md](STDLIB.md).

## Building

```
make verify   # prove zero dependencies, write deps-proof.txt
make test     # the whole suite, on node:test
make build    # dist/nirdep/ and dist/nirdep-<version>.tar.gz
make repro    # build twice, print both hashes, fail unless identical
```

`make build` writes its own tar. Not because writing a tar writer is fun, but
because the archive has to be reproducible and the usual suspects for
irreproducibility all live in tar and gzip metadata: file mtimes, uid and gid,
directory iteration order, and the timestamp gzip stamps into its own header.
Every one of those is pinned. `make repro` publishes both hashes and refuses to
claim the bonus if they differ. GNU tar reads the result, so this is interop and
not a private format that only we can open.
